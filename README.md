# GPU HashMap Engine

A CUDA prototype for batched associative operations on variable-length byte
keys, implemented in a deliberately procedural C style. Four threads cooperate
on each key, compute three independently seeded XXH32 hashes from the same input
loads, attempt three primary slots, and fall back to a linear-probed overflow
table. Hashes only select candidates: stored length and every key byte are
compared before a lookup succeeds.

The included file comparator is an end-to-end correctness harness for the map.
It is not a claim that hashing is the fastest way to compare two files.

> **Current status:** the current procedural tree passes a warning-free native
> release build, the GPU/CPU XXH32 vectors, the forced-overflow lookup/deletion
> regression, and the deterministic file matrix on an NVIDIA GeForce RTX 2070
> SUPER (`sm_75`). Compute Sanitizer memcheck also reports zero errors and zero
> leaked bytes for both focused tests and the end-to-end comparator. Racecheck,
> initcheck, synccheck, and reproducible performance characterization remain
> pending.

> **AI assistance disclosure:** All test code and test fixtures in this
> repository were generated by AI and executed by the project author on the
> target hardware. This README was written and polished with AI assistance.

## Engineering objective

This project started from a simple question: what changes when a hash table for
byte strings is designed around SIMT execution rather than copied from a CPU?

The implementation focuses on four coupled problems:

1. **Hashing** — expose useful parallel work inside each variable-length key.
2. **Indexing and storage** — keep table metadata compact and key bytes stable.
3. **Collision handling** — limit the common path to a few candidates without
   making collisions equivalent to key equality.
4. **Growth and lifetime** — make capacity failures explicit now, then add
   resizing and reclamation only after the fixed-capacity design is verified.

The current version is a correctness-first baseline for studying atomics,
memory traffic, divergence, register pressure, occupancy, and probe behavior.
It deliberately does not publish performance claims before those effects are
measured.

## Technical summary

| Property | Implementation |
| --- | --- |
| Key representation | Concatenated `uint8_t` arena plus `offset[]` and `length[]` |
| Value representation | Any `uint32_t`; presence is returned in a separate byte |
| Work assignment | One `cooperative_groups::thread_block_tile<4>` per key |
| Hash path | Three seeded XXH32 states computed in one traversal |
| Primary placement | Three direct candidates, each claimed with `atomicCAS` |
| Overflow path | Separate structure-of-arrays table with linear probing |
| Collision check | Stored length plus cooperative full-byte comparison |
| Deletion | Atomic live-offset-to-tombstone transition |
| Capacity | Fixed, explicit, workload-derived in the CLI |
| Host code | Plain structs/functions, C allocation and I/O, explicit CUDA cleanup |
| Target | Turing TU104, RTX 2070 Super, compute capability 7.5 |

### Implementation style

Project-owned host and test code intentionally avoids classes, inheritance,
templates, exceptions, iostreams, and STL containers. State lives in plain
structs; operations are free functions; ownership is visible through paired
`malloc`/`free` and `cudaMalloc`/`cudaFree` calls. The `.cu` files are still
compiled with `nvcc -std=c++17` because CUDA and the
`cooperative_groups::thread_block_tile<4>` API require C++ compilation. That
four-lane tile is the one deliberate use of a C++ template API in the kernel
path, not an object-oriented host design.

## Design lineage: research ideas versus this implementation

The original README and project notes explored a wider design space than the
current code implements. This table makes that boundary explicit instead of
presenting proposed optimizations as completed work.

| Idea from the original README and research notes | Current state | Technical consequence |
| --- | --- | --- |
| Batched insert and lookup kernels | Implemented | One logical key is assigned to each four-thread tile in a grid-stride loop |
| Four threads cooperate on one XXH32 key | Implemented | One hardware warp contains eight independent key tiles |
| Three hash choices | Implemented | Three seeded XXH32 results select three primary candidates |
| Overflow/stash table | Implemented | Failed three-choice placement falls back to a separate linear-probed table |
| Separate key and metadata storage | Implemented | Bytes live in one arena; slots store offset, length, and value as structure-of-arrays metadata |
| Warp shuffle for hash reduction | Implemented | Per-lane accumulators are gathered with `tile.shfl()` |
| Remove a second "master offset" indirection | Implemented | Slots directly store offsets into the owned byte arena |
| One-, two-, and four-thread paths selected by key length | Not implemented | Every non-empty key currently pays for a four-thread tile, including keys shorter than 16 bytes |
| Double-buffered tile loading | Not implemented | Copy, hash, and probe phases are not software-pipelined across keys |
| Quotient/remainder or double-hash probe stepping | Not implemented | Overflow uses simple linear probing |
| Input pre-sort for coalescing | Not implemented | Tiles consume keys in caller-supplied order |
| Compact fingerprints before full comparison | Not implemented | Occupied candidates require a length check and potentially a full byte comparison |
| Dynamic resize/rehash | Not implemented | Both tables and the key arena have fixed capacities |

This is **three-choice hashing with overflow**, not cuckoo hashing. A cuckoo
insertion relocates resident keys; this implementation never evicts or
recursively moves an existing entry. The current tree is a correctness baseline
for testing the remaining ideas, not evidence that every idea in the research
notes is already useful.

## System architecture

The map separates key storage from slot metadata:

```text
input batch
  bytes[]       concatenated key bytes
  offsets[i]    key i's start in bytes[]
  lengths[i]    key i's exact byte length
  values[i]     key i's 32-bit payload

device-resident map
  master_bytes[]        append-only key arena

  key_offsets[]         primary slot -> arena offset / sentinel
  key_lengths[]         primary slot -> key length
  values[]              primary slot -> payload

  overflow_offsets[]    overflow slot -> arena offset / sentinel
  overflow_lengths[]    overflow slot -> key length
  overflow_values[]     overflow slot -> payload
```

Each key has an explicit `(offset, length)` pair. The batch therefore does not
need an `offset[key_count]` terminal sentinel, and the general hashmap path does
not require keys to be padded to a 16-byte boundary. Complete stripes and byte
tails are handled separately. The file comparator's zero padding is specific to
its fixed 20-byte `(chunk index || 16 data bytes)` encoding.

`HashmapEngine` is a device-resident descriptor containing capacities, arena
state, and pointers to those allocations. The host first creates the arrays
with `cudaMalloc`, places their device virtual addresses into a host-side
descriptor, and copies the descriptor itself to device memory.

### Address spaces and the runtime/driver boundary

The host uses the CUDA Runtime API. The Runtime establishes a CUDA context
implicitly, loads the device image, allocates GPU-accessible virtual memory,
marshals kernel parameters, and calls into the CUDA driver. The relevant
software path is:

```text
gpu-hashmap process
    -> CUDA Runtime (libcudart)
    -> CUDA Driver API / user-mode driver (libcuda)
    -> NVIDIA kernel driver
    -> GPU command processor and SMs
```

A pointer returned by `cudaMalloc()` is not a CPU physical address and not a
raw VRAM offset. It is a device pointer in a GPU virtual-address space managed
by the CUDA driver. Copying `HashmapEngine` to the device copies those pointer
values; it does not copy the separately allocated arrays they reference.

CPU virtual addresses, GPU virtual addresses, and any I/O virtual addresses
used for DMA are distinct translation domains even when Unified Virtual
Addressing makes some pointer values comparable at the API level. Ordinary host
code must not dereference the `cudaMalloc()` fields in the host-side descriptor.
`cudaMemcpy()` requests a transfer through the runtime/driver; it is not a CPU
load/store into a guessed physical VRAM address.

A launch such as `insert_kernel<<<grid, block>>>(d_engine, ...)` also has an ABI
boundary. The Runtime marshals the descriptor pointer, array pointers, and
32-bit scalar arguments into kernel parameter space, resolves the kernel in the
loaded device module, and submits the launch through the driver. The first
kernel dereference of `d_engine` occurs on the GPU.

Below the CUDA API boundary, the driver owns the mechanisms discussed in the
notes: GPU page-table/GMMU mappings, channel and runlist construction,
pushbuffer submission, PBDMA/PFIFO scheduling, MMIO/BAR access, and DMA setup.
Those mechanisms explain how an allocation and launch reach the hardware, but
this repository does **not** program BAR registers, build RAMFC/channel state,
write GMMU page tables, or submit raw FIFO methods. They are architectural
context, not hidden code in this project.

The tables use a structure-of-arrays layout. Probing an offset does not
automatically fetch the corresponding value or length, and primary and overflow
metadata have the same representation.

### Slot-state encoding

The offset word doubles as the atomically updated slot state:

| Offset | Meaning |
| ---: | --- |
| `0xFFFFFFFF` | Empty: the probe sequence has never occupied this slot |
| `0xFFFFFFFE` | Tombstone: an entry was deleted here |
| `< 0xFFFFFFFE` | Live offset into `master_bytes` |

A separate `found[]` output means `0xFFFFFFFF` remains a valid user value.
Because two 32-bit offsets are reserved as sentinels, the arena must remain
smaller than `0xFFFFFFFE` bytes.

The sentinels are named unsigned constants rather than the earlier prototype's
literal `-1`. That removes signed-to-unsigned `atomicCAS` comparisons and their
warning-prone implicit conversions.

Ignoring allocation alignment and the descriptor itself, persistent storage is
approximately

```text
byte_capacity
  + 12 * primary_capacity
  + 12 * overflow_capacity
  + 4 bytes for failed_inserts
```

Key storage is append-only. Deletion changes table metadata but does not reclaim
arena bytes.

## Mapping XXH32 onto a four-thread tile

XXH32 processes a 16-byte stripe with four independent 32-bit accumulators. The
kernel maps that structure directly onto four lanes:

| Tile lane | Bytes in each stripe | Initial accumulator |
| ---: | --- | --- |
| `0` | `0..3` | `seed + PRIME1 + PRIME2` |
| `1` | `4..7` | `seed + PRIME2` |
| `2` | `8..11` | `seed` |
| `3` | `12..15` | `seed - PRIME1` |

Each lane loads one little-endian word and applies the XXH32 round:

```text
acc += word * PRIME2
acc  = rotl(acc, 13)
acc *= PRIME1
```

The implementation maintains three accumulator sets per lane:

```text
seed 0 = 0x9E3779B1
seed 1 = 0x517CC1B7
seed 2 = 0x85EBCA6B
```

One loaded word is therefore reused across all three seeded states. After all
complete stripes, every lane participates in `tile.shfl` operations that form
the standard XXH32 merge:

```text
rotl(v1, 1) + rotl(v2, 7) + rotl(v3, 12) + rotl(v4, 18)
```

Lane 0 owns the three merged states, handles the remaining 4-byte and 1-byte
tails, and executes the avalanche. Lookup and deletion broadcast lane 0's
results back across the tile before cooperative comparison.

For each seed, the scalar finish follows the XXH32 sequence:

```text
h += length
for each remaining 4-byte word:
    h += word * PRIME3
    h  = rotl(h, 17) * PRIME4
for each remaining byte:
    h += byte * PRIME5
    h  = rotl(h, 11) * PRIME1
h ^= h >> 15; h *= PRIME2
h ^= h >> 13; h *= PRIME3
h ^= h >> 16
```

The three seeds provide three placement choices; they do not make XXH32
cryptographic and do not make the outputs mathematically independent. Exact
key comparison remains mandatory.

### Alignment policy

Keys may begin at arbitrary byte offsets. `load_u32_le` therefore assembles a
32-bit word from four bytes instead of dereferencing an unaligned
`uint32_t*`. This preserves XXH32 semantics on every offset and creates a safe
baseline for a future aligned/vectorized fast path.

### Utilization tradeoff

A four-lane tile matches the 16-byte stripe well, but not every key length:

- A 256-thread block contains eight warps, 64 four-thread tiles, and therefore
  handles 64 keys per grid-stride iteration.
- Keys shorter than 16 bytes use the scalar XXH32 path in lane 0; lanes 1–3 do
  little useful work.
- Tail processing is serialized in lane 0.
- The file harness uses 20-byte keys: one cooperative 16-byte stripe followed
  by one scalar 4-byte tail.
- Insertion currently reads the input key once to copy it into the arena and
  again to hash it.

The project therefore treats “four threads per key” as a hypothesis to profile,
not a universal optimum. The relevant experiment is one versus two versus four
threads across real key-length distributions.

## Kernel work mapping

All map kernels require `blockDim.x % 4 == 0`. For each lane:

```cpp
global_thread = blockIdx.x * blockDim.x + threadIdx.x;
first_key     = global_thread / 4;
key_stride    = gridDim.x * blockDim.x / 4;
```

Integer division maps four consecutive threads to one key. The tile then uses a
grid-stride loop so the launch size is independent of the batch length.

The CLI uses 256 threads per block and computes

```text
blocks = max(1, min(ceil(4 * key_count / 256), 4 * SM_count))
```

The `4 * SM_count` term is only a grid-size heuristic. It is not an occupancy
calculation. On the 40-SM RTX 2070 Super it caps the launch at 160 blocks;
actual residency still depends on compiled register usage, shared memory, and
architectural block limits.

### What the four-thread tile means on Turing

`thread_block_tile<4>` is a logical Cooperative Groups partition, not a native
four-thread scheduling unit. The RTX 2070 Super executes 32-thread warps, so one
warp contains eight tiles working on eight different keys. The warp remains the
instruction-issue unit even though Turing maintains per-thread program state.
If the eight tiles take different collision or probe paths, those paths can
diverge and execute serially within the warp.

For Turing, the relevant architectural limits are four warp schedulers per SM,
at most 32 resident warps per SM, at most 16 resident blocks per SM, 65,536
32-bit registers per SM, and up to 64 KiB shared memory per SM. A 256-thread
block is eight warps, so the thread/warp limit alone permits no more than four
such blocks per SM. Register allocation can lower that number; the current
kernel uses no dynamic or static shared-memory array, so shared-memory capacity
is not presently the limiting resource.

Ignoring registers and all pipeline effects, the launch geometry has this
upper-bound bookkeeping:

| Quantity | Derivation | Upper bound |
| --- | ---: | ---: |
| Warps per 256-thread block | `256 / 32` | `8` |
| Four-thread key tiles per block | `256 / 4` | `64` |
| Blocks per SM from the thread/warp limit | `1,024 / 256` | `4` |
| Resident key tiles per SM from that limit | `4 * 64` | `256` |
| Resident key tiles across 40 SMs | `40 * 256` | `10,240` |

That is a residency ceiling, not “10,240 keys execute simultaneously” and not
a throughput prediction. The grid cap of 160 blocks merely supplies enough
blocks for four per SM when other resource limits allow it; instruction issue,
dependencies, memory behavior, and atomics still determine progress.

The “four schedulers” fact does **not** mean that 128 threads each complete an
arbitrary instruction every clock. Each scheduler selects an eligible warp and
issues according to the architecture's pipelines and instruction latencies.
For this implementation, physical register count, eligible warps, divergence,
memory latency, and atomic contention matter more than multiplying scheduler
count by warp width.

XXH32 is dominated by 32-bit integer adds, multiplies, rotates/shifts, XORs, and
loads. It does not use the Turing SM's FP32 or Tensor Core datapaths, so peak
TFLOP/s and Tensor throughput are irrelevant performance denominators for this
kernel. Turing's separate FP32 and INT32 execution resources help workloads that
can overlap floating-point and address/integer work; this predominantly integer
kernel must instead be evaluated against its issued integer instructions,
memory stalls, and atomic behavior.

For a key shorter than 16 bytes, the scalar XXH32 path is owned by lane 0 of
each tile. During that hash portion only eight lanes in a 32-lane warp perform
the scalar work: 25% useful lane participation for that region, not necessarily
25% utilization for the entire kernel. The copy, comparison, and control-flow
regions have different participation patterns and must be measured separately.

## Batched insertion

Insertion is intentionally split into two launches:

1. `reserve_batch_kernel<<<1,1>>>` validates capacity, publishes one
   `batch_base`, and advances the arena bump pointer.
2. `insert_kernel` copies keys into the reserved range, hashes them, and places
   their metadata.

`master_byte_current` always denotes the **next free byte**, not the last byte
already written. Reservation snapshots the old value into `batch_base`, checks
`total_bytes <= byte_capacity - current` without overflow, and then advances
the counter by the complete batch size.

This separation fixes a fundamental cross-block synchronization problem.
`__syncthreads()` is a block barrier; it cannot publish a value safely to an
arbitrary grid. Sequential kernel launches in the same stream give every insert
block a common, fully committed batch base.

For each key, lane 0 computes the primary candidates

```text
s1 = h1 % primary_capacity
s2 = h2 % primary_capacity
s3 = h3 % primary_capacity
```

and claims the first empty or tombstone slot with `atomicCAS`. If all three are
occupied, overflow probing starts at

```text
((h1 ^ h2 ^ h3) * 0x9E3779B9) % overflow_capacity
```

and scans at most the complete overflow capacity. Failed placement increments a
device counter; the host treats any non-zero count as an error instead of
silently dropping keys. Reserved arena space from a failed insertion is not
rolled back.

## Lookup and collision correctness

A 32-bit hash is never accepted as proof of equality. For every primary or
overflow candidate:

1. Lane 0 reads the slot offset, stored length, and value.
2. Tile shuffles broadcast that metadata.
3. Empty and tombstone states are rejected before an arena dereference.
4. The stored range is validated against `master_byte_current`.
5. Stored and query lengths must match.
6. Lane `r` compares bytes `r, r+4, r+8, ...`.
7. `tile.any(different)` rejects the candidate if any lane finds a mismatch.

Lookup checks all three primary candidates. If none matches, it follows the
same overflow sequence used by insertion. A never-used slot terminates the
search; a tombstone does not.

Every query initializes its outputs:

```text
missing: found[i] = 0, results[i] = 0
matched: found[i] = 1, results[i] = stored_value
```

No payload value is overloaded as a not-found sentinel.

## Deletion

Deletion repeats the complete search and exact comparison, then atomically
replaces the live offset with the tombstone sentinel:

```text
atomicCAS(slot_offset, live_offset, 0xFFFFFFFE)
```

The distinction between empty and tombstone preserves overflow probe chains:

```text
EMPTY      -> nothing was ever inserted here; lookup may stop
TOMBSTONE  -> an entry existed here; lookup must continue
```

The current implementation does not compact clusters, reclaim bytes, or trigger
a rehash when tombstones accumulate.

## File-comparison harness

For a file of `S` bytes, the executable creates
`N = ceil(S / 16)` fixed-size 20-byte keys:

| Key bytes | Meaning |
| --- | --- |
| `0..3` | Little-endian 32-bit chunk index |
| `4..19` | Sixteen bytes of file data; the final chunk may be zero-padded |

The value associated with chunk `i` is also `i`.

Position is part of the key because inserting bare chunks would test unordered
membership. Reordered chunks, duplicate chunks, and multiplicity changes could
otherwise be misclassified.

The exact comparison procedure is:

1. Read both inputs in binary mode.
2. Reject different byte sizes before GPU work.
3. Return identical immediately for two empty files.
4. Insert file A's `(position || chunk, position)` pairs.
5. Query file B's positioned chunks.
6. Require `found[i] == 1 && results[i] == i` for every `i`.

Checking original file size before encoding makes zero padding in the last key
unambiguous. Even if XXH32 collides, the full 20-byte key comparison prevents a
false identical verdict.

The harness sizes the map as

```text
primary_capacity  = next_pow2(max(64, 2 * N))
overflow_capacity = next_pow2(max(64, floor(N / 4) + 1))
byte_capacity      = 20 * N
```

so the primary load target is at most 0.5 before the overflow reserve.

## Correctness invariants

| Invariant | Why it matters |
| --- | --- |
| Block size is divisible by four | Cooperative tiles and key indexing remain complete |
| `start <= total_bytes` and `length <= total_bytes - start` | Avoids overflow-prone `start + length` bounds checks |
| Arena offsets are below `0xFFFFFFFE` | Keeps live offsets distinct from both sentinels |
| Reservation completes before insertion | All blocks observe the same batch base |
| Mutation and lookup do not overlap | Length/value publication is visible before readers run |
| Overflow lookup uses insertion's complete probe sequence | Every successfully inserted overflow key remains reachable |
| Lookup stops only at `EMPTY`, never at `TOMBSTONE` | Deletion cannot sever a probe chain |
| Key length and bytes are checked | Hash collisions and prefix matches cannot become false hits |
| `found[]` is distinct from `results[]` | All `uint32_t` payloads remain representable |

The earlier prototype violated several of these conditions; the current table
keeps the corrected contracts beside the implementation they constrain.

## Work and storage complexity

Let `L` be key length and `p` the number of overflow slots visited.

| Operation | Work per key | Qualification |
| --- | --- | --- |
| Hash | `O(L)` | Three seeded states share each 16-byte stripe load |
| Insert | `O(L + p)` plus at most three primary claims | Copying and hashing currently make separate input passes |
| Lookup | `O(L)` hash plus up to `O((3+p)L)` comparison | Occupied non-matching candidates can require a full key read |
| Delete | Lookup cost plus one successful CAS | Tombstones and arena bytes remain allocated |

The table stores neither the original hash nor a short fingerprint. A compact
fingerprint could reject most occupied non-matches before fetching key bytes,
but it would add metadata traffic and another publication field. That tradeoff
is intentionally left for measurement.

## Memory-access behavior

CUDA runtime allocations are aligned to at least 256 bytes, but that does not
make every key aligned: `bytes + offsets[i]` can begin at any byte. The file
harness happens to use a 20-byte stride, while the hashmap API accepts arbitrary
offsets. `load_u32_le()` therefore performs byte-safe little-endian assembly
instead of assuming `uint32_t` alignment. This is a correctness choice; whether
the generated SASS combines any of those byte operations is a compiler question
to inspect, not a source-level guarantee.

The access patterns differ by phase:

- **Arena copy:** the four lanes of a tile copy indices `lane, lane+4, ...`.
  They collectively cover one key, but the eight tiles in a warp are separated
  by the caller's key layout.
- **Hash stripes:** a tile consumes 16 adjacent bytes per stripe. Across the
  full warp, there are eight independent 16-byte regions rather than one
  guaranteed 128-byte contiguous transaction.
- **Primary metadata:** only lane 0 of each tile probes its three hash-derived
  slots. Up to eight lanes in a warp therefore issue scattered slot accesses;
  slots that collide also serialize at `atomicCAS`.
- **Overflow metadata:** linear probing creates locality within one tile over
  time, but different tiles normally begin at unrelated slots and can diverge
  in probe count.
- **Exact comparison:** all four tile lanes reread the stored arena bytes. An
  occupied hash candidate with the right length can therefore cost a full key
  read even when the final byte comparison fails.

Shared-memory staging is not automatically a win here. Insert currently rereads
the input between arena copy and hashing, and lookup can reread a query between
hashing and candidate comparison, so there is potential **intra-tile** reuse.
There is no **inter-tile** reuse, however, and variable-length staging consumes
shared-memory capacity plus synchronization. A fair experiment should compare
staging with a fused copy/hash path and with cache behavior in the existing
path. The original notes identify shared memory as a hypothesis; they do not by
themselves establish that it reduces traffic.

## CUDA compilation path

`nvcc` separates host and device compilation trajectories. Host code is passed
to the host compiler, while device code is lowered through NVIDIA's device
toolchain and embedded in the host object as a GPU image/fatbinary:

```text
CUDA translation unit
  -> host C++ -> host compiler -> host object
  -> device C++ -> NVVM IR -> PTX -> ptxas -> sm_75 SASS/cubin
  -> host object containing embedded device image
```

PTX is a virtual ISA; SASS is the native instruction encoding executed by this
GPU generation. This build asks `ptxas` for an `sm_75` cubin ahead of time. A
CUDA application may also embed PTX for driver JIT compilation, but that is a
separate compatibility path and should not be confused with the concrete SASS
whose registers and instructions are profiled here.

`hash3_xxh32` is defined in `src/hash.cu`, while kernels that call it are in
`src/hashmap.cu`. That cross-translation-unit device call is why the Makefile
uses `-rdc=true`: each object contains relocatable device code and the final
`nvcc` link performs device linking before host linking. Removing `-rdc=true`
without moving/inlining the definition into the caller translation unit would
break that link model.

At the PTX level, globally launched kernels are entry functions (`.entry`) and
non-kernel device routines are functions (`.func`) when they survive
optimization as calls. Kernel arguments enter through parameter space
(`.param`); pointer parameters carry device virtual addresses that global-memory
instructions later dereference. Source operations commonly map as follows:

| CUDA source concept | PTX-level concept | Typical SASS-level form on Turing |
| --- | --- | --- |
| `threadIdx.x`, `blockIdx.x` | special-register reads such as `%tid.x`, `%ctaid.x` | `S2R` from a special register |
| pointer/index arithmetic | `mul`, `add`, `mad.wide` or equivalent | often folded into `IMAD`/`IMAD.WIDE` sequences |
| arena/metadata load | `ld.global` | `LDG`-family instruction |
| arena/metadata store | `st.global` | `STG`-family instruction |
| `atomicCAS` | `atom.global.cas` or compiler equivalent | global atomic instruction sequence |
| `tile.shfl` | warp shuffle operation plus active-mask handling | `SHFL`-family instruction |

These are expected lowering patterns, not promises about an exact instruction
sequence. Only the emitted PTX and cubin for a specific compiler/build establish
what was generated.

PTX registers are unbounded virtual names in an intermediate ISA; they are not
the 65,536 physical 32-bit registers in a Turing SM. `ptxas` performs liveness
analysis, assigns physical registers, and may spill excess live state to local
memory. The three concurrent XXH32 accumulator chains intentionally reuse each
loaded word, but also keep more state live. Occupancy analysis must therefore
start from `ptxas`/cubin resource usage, not a count of variables in the source
or PTX text.

Release builds use `-O3 -lineinfo`; debug builds use `-O0 -g -G`. Useful
inspection commands are:

```bash
nvcc -Xptxas=-v ...
cuobjdump --dump-resource-usage ./gpu-hashmap
cuobjdump --dump-ptx ./gpu-hashmap       # if PTX is embedded
cuobjdump --dump-sass ./gpu-hashmap
ncu --set full ./gpu-hashmap test/file_a.bin test/file_b.bin
```

## Build and run

Requirements:

- Linux
- NVIDIA GPU and compatible driver
- CUDA Toolkit with `nvcc`
- GNU Make
- Python 3 for generated test fixtures
- Compute Sanitizer and Nsight Compute for the corresponding targets

Build for the RTX 2070 Super:

```bash
git clone https://github.com/mxrse834/gpu-hashmap-engine.git
cd gpu-hashmap-engine

make CUDA_ARCH=sm_75
./gpu-hashmap path/to/file-a path/to/file-b
```

Override the architecture for another GPU:

```bash
make CUDA_ARCH=sm_86
```

The executable returns:

| Exit code | Meaning |
| ---: | --- |
| `0` | Files are byte-for-byte identical |
| `1` | Files differ |
| `2` | Invalid arguments, I/O/capacity failure, or a CUDA runtime/kernel error |

### What that fixture actually launches

The reported 2,217-byte file is useful for checking the host/kernel arithmetic,
but it is intentionally too small to be a throughput benchmark:

```text
file bytes             = 2,217
keys                    = ceil(2,217 / 16) = 139
encoded input bytes     = 139 * 20 = 2,780
primary capacity        = next_pow2(max(64, 2 * 139)) = 512
overflow capacity       = next_pow2(max(64, floor(139 / 4) + 1)) = 64
launch                  = ceil((4 * 139) / 256) = 3 blocks
logical tile slots      = 3 * (256 / 4) = 192
unused tile slots       = 192 - 139 = 53
```

Ignoring allocator rounding and the descriptor, the persistent map allocations
for this run total

```text
2,780 + 12 * 512 + 12 * 64 + 4 = 9,696 bytes
```

The nominal key-count-to-primary-capacity ratio is `139 / 512`, about 27.1%,
before accounting for any keys routed to overflow. More importantly, three
blocks can occupy no more than three SMs at once. On the 40-SM test GPU, this
fixture validates correctness and edge behavior but cannot establish
device-saturating throughput.

The `hashmap-test` regression forces three keys into one overflow
cluster, verifies lookup from the raw-hash-derived start slot, deletes the first
key in that cluster, and verifies that later keys remain reachable through the
tombstone. Its observed terminal line is:

```text
forced-overflow lookup/delete: PASS
```

The hash test includes empty input, `a`, `abc`, concatenated keys with unaligned
starts, and the 15/16/17/65-byte boundaries under all three seeds. Before the GPU
comparison, the CPU implementation checks the published zero-seed XXH32 values
for empty input and `abc`.

The original compile command passed `-Wpedantic` through `nvcc`, which caused
GCC to warn on `#line` directives generated by CUDA and used throughout
`cooperative_groups.h`. The Makefile intentionally retains `-Wall -Wextra` but
does not apply that incompatible host policy flag.

## Performance questions—not claims

The current implementation is designed to make the following measurements
possible. Any benchmark should record GPU, driver, CUDA version, build flags,
table capacities, load factor, key-length distribution, warm-up policy, and
whether timing covers kernels or the complete host/device path.

A defensible experiment matrix should vary one design axis at a time:

| Axis | Minimum useful cases |
| --- | --- |
| Threads per key | `1`, `2`, current `4`, and one full warp |
| Key length | `0`, `1..15`, `16`, `17..31`, `32`, `64`, `128+` bytes |
| Primary load factor | approximately `0.25`, `0.50`, `0.70`, `0.85` |
| Query mix | all hits, all misses, and controlled hit/miss mixtures |
| Key/hash distribution | uniform, repeated prefixes, skewed/Zipf-like, and deliberately colliding candidates |
| Batch scale | launch-bound small batches through device-saturating batches |
| Build | optimized `sm_75` cubin; debug/sanitized results reported separately |

Kernel timing should use CUDA events around warmed launches. End-to-end timing
should be reported separately because allocation, copies, host I/O, and the
current synchronization policy are not kernel work. At minimum, retain:

- keys/s and input GiB/s, with median and tail latency over repeated runs;
- `ptxas` registers per thread, spill loads/stores, static shared memory, and
  theoretical active blocks/warps per SM;
- achieved occupancy and eligible/active warp behavior;
- branch divergence and active-lane behavior across the eight tiles per warp;
- global-memory sector/request efficiency for arena and metadata traffic;
- atomic activity/contention, primary-choice success rate, overflow fraction,
  and the complete probe-length histogram.

Metric names can change between Nsight Compute releases, so reports should keep
the CUDA/Nsight version and the raw `.ncu-rep` artifact rather than publishing
only a screenshot or one derived percentage.

1. At what key lengths does a four-lane tile outperform one thread per key?
2. What physical register count results from three accumulator sets per lane,
   and how does it affect achieved occupancy?
3. What is the global-load cost of byte-safe word assembly relative to an
   aligned/vectorized path?
4. How much warp efficiency is lost when eight independent tiles in one warp
   take different primary and overflow paths?
5. How does atomic contention scale with primary-table load factor?
6. What is the overflow probe-length distribution, and which stall reasons
   dominate long chains?
7. For small batches, how much time is host I/O, allocation, transfer, and the
   deliberate post-launch synchronization rather than kernel execution?
8. Would a stored fingerprint save enough arena traffic to pay for its metadata?

The current kernel does not stage keys in shared memory. The relevant comparison
is existing rereads versus shared-memory cost versus a fused copy/hash path—not
"shared is faster" in isolation. L1 behavior and global-load efficiency should
be measured with Nsight rather than assumed.

## Known limitations

- The procedural host allocation helpers are internal to `main.cu`; this is not
  yet a reusable C API.
- Duplicate-key insertion and update behavior are undefined.
- Capacity is fixed; there is no resize or rehash path.
- Arena storage and tombstones are never reclaimed.
- Insert, lookup, and delete are ordered phases in one stream. Concurrent
  readers/writers and multi-stream mutation are unsupported.
- Overflow probing is controlled by lane 0 and can generate divergence and
  poorly coalesced accesses.
- Indexing uses `%` even though the CLI chooses power-of-two capacities. An
  enforced mask-based specialization is not implemented.
- Full comparison is byte-granular and no slot fingerprint is stored.
- `check_kernel` calls `cudaDeviceSynchronize()` after every launch for precise
  fault attribution; this is unsuitable for an asynchronous throughput API.
- Randomized reference-map testing and adversarial forced-collision tests still
  need to be added.

## Roadmap

1. Complete `initcheck` and `synccheck` on the RTX 2070 Super; record
   `racecheck` separately with its shared-memory-only scope.
2. Add randomized CPU-reference tests for insert, lookup, delete, overflow
   chains, capacity exhaustion, and the full `uint32_t` value range.
3. Benchmark one-, two-, four-, and warp-cooperative mappings by key length.
4. Add an aligned load specialization while preserving the byte-safe fallback.
5. Measure power-of-two mask indexing and a stored fingerprint.
6. Evaluate warp-cooperative and quotient/remainder-style overflow strategies.
7. Define update semantics, resize/rehash, tombstone compaction, and arena
   reclamation.
8. Build a stream/event-based host API with pinned staging buffers after the
   synchronous reference path is stable.
9. Track PTX, SASS, `ptxas` resource use, occupancy, and Nsight reports against
   commits before making performance claims.
